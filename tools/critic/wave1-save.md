## Score: 7/10   (pass bar 8)  → FAIL (round 1/3)

The engineering core is solid: the round trip is lossless including RNG continuation and clock, the 2 MB budget is enforced with diagnostics, migrations are a real ordered list with a newer-version refusal, corrupt data is caught and the game returns to a legal state, and the store falls back IndexedDB → localStorage → memory. What keeps it under the bar is the "autosave/quicksave work" clause of the rubric row: the quicksave key clobbers manual slot 1, the new-game autosave is the one path that is not state-gated and will fire inside the intro cutscene/dialogue, three of the five §5.7 autosave triggers are not wired (one of them, `chapter-changed`, is available on the core bus today), thumbnails will be blank in a real browser, and the success path of `SaveService.load()` is not covered by a test. All fixes are small and local; this should pass in one round.

## What the evidence shows (bullets, cite screenshot or number)

- Lossless round trip: test 1 builds 5000 entities with Transform/Name/Character/Skills/Inventory, gzips, decodes, migrates, applies to a fresh host and asserts `JSON.stringify(host2.world.serialize()) === JSON.stringify(host1.world.serialize())`, `clock.time` equal, `playtimeSec` 12345, `seed` 42, and `rng.world.next()` equal to the original stream's next value (`save.test.ts:99–130`). RNG continuation is therefore proven, not claimed.
- Size: 5000 entities → 211,850 bytes gzip (10 % of budget). `encodeSave` throws when `out.byteLength > SAVE_MAX_BYTES` and logs the five largest component types (`db.ts:297–304`). The throw path itself has no test (see issue 8).
- Compression: gzip via `CompressionStream` with a 1-byte encoding header; raw fallback proven by deleting `CompressionStream` in test 2 (`db.ts:282–306`, `save.test.ts:133–155`).
- Migrations: ordered `[{from,to,migrate}]` list, `migrateToCurrent` walks forward, throws "newer" for `schemaVersion > SAVE_SCHEMA_VERSION`, throws on a missing path. v0→v1 (`questFlags`→`flags`) is an honest worked example, labelled as such in the source; both directions tested (`migrations.ts`, `save.test.ts:158–170`).
- Corrupt data: `decodeSave` distinguishes no-data / bad gzip / unknown header / bad JSON; `load()` wraps everything in try/catch, toasts "Could not load save", turns the loading overlay off and requests `title` (`index.ts:74–79`); test asserts `stateEvents === ['loading','title']` and the toast (`save.test.ts:178–194`). `load()` never leaves the machine in `loading` on the failure path.
- Storage: `IndexedDbStore` (db `eidgenossen`, store `saves`, keyPath `slot`) per §5.7; `ResilientStore` switches to `LocalStorageStore`/`MemoryStore` the first time IndexedDB throws (private mode) (`db.ts:187–230`). `list()` on an empty store returns `[]` from `getAll()`; `hasAny()` derives from it. Only `MemoryStore` is tested.
- Restore order (`index.ts:46–72`): `resetWorld → reseed → rng.restore → world.load → clock.set → playtimeSec`, then `quest.restore`, `exploration.setDiscovered`, then `'loaded'` is emitted **after** the world is populated (correct), then `world.streamAround(player)` before the state flips to `explore`/`combat`, matching "Load performs `world.streamAround` before fade-in" in §5.7. `rng.restore` tolerates a missing `combat` stream (`rng.ts:140–143`).
- Transient components: the module calls `world.serialize()` and never re-adds `MeshRef`/`Velocity`/other transient types; exclusion stays core's job (`ecs.ts:184`). Verified.
- Module isolation: every import in `src/save/*.ts` is `@core/*` or `./` — nothing from `src/world|party|exploration|combat|quest|ui`. `SaveHost` (`host.ts`) is a structural slice of `GameContext`, which is why the tests run headless without a WebGL renderer — a good design.

- Combat: `buildSnapshot` includes `combat.serialize()` only when `combat.isActive()`; if `serialize()` returns `null` the block is silently omitted (issue 6).

## Ranked issues (if FAIL, or notable even on PASS)

1. **Quicksave overwrites manual slot 1.** `QUICKSAVE_SLOT = 1` (`index.ts:16`) but §3.4 defines `slot: 0 = autosave, 1..5 manual` and §2 budgets "5 slots + autosave". A player who saves manually into slot 1 and then presses F5 loses that save. — evidence: `index.ts:16, 204`; ARCHITECTURE §3.4 line 167. — fix: reserve a dedicated quicksave slot outside the manual range (e.g. `QUICKSAVE_SLOT = 6`, and document `0 = autosave, 1..5 manual, 6 = quicksave` in the SaveFile comment via a §10 core change request), or make F5 target "the most recently used manual slot" — the former is simpler and what Skyrim-style games do.

2. **New-game autosave is not state-gated and will fire inside the intro cutscene/dialogue.** `ctx.events.on('new-game', () => setTimeout(triggerAutosave, 2000))` calls `triggerAutosave()` directly (`index.ts:149–151`), bypassing `requestAutosave()`. `main.ts:125–126` emits `'new-game'` and immediately calls `quest.start('quest.der-eid')`, which (per the rubric's act1 row) opens the Rütli/oath scene — so 2 s later the autosave fires during a cutscene or dialogue, violating "autosave never fires in combat/dialogue/cutscene". In harness `combat-morgarten-setup` / `combat-brunnen-quay`, `loadScenario` runs `newGame` then `combat.start` at once, so the same timer fires mid-combat. — evidence: `index.ts:149–151` vs `index.ts:157–160`; `main.ts:125–126, 163, 201`. — fix: replace the `setTimeout(triggerAutosave, …)` body with `requestAutosave()` (which already defers to the next `explore` tick), or set `pendingAutosave = true` and let the scheduler system pick it up; drop the timer entirely.

3. **Three of the five §5.7 autosave triggers are missing.** Implemented: quest complete/advance, 10-minute timer (plus the un-specified new-game save). Not implemented: **new chapter**, **encounter start (with combat block)**, **fast travel**. `'chapter-changed'` already exists on the core `GameEvents` bus (`events.ts`) and can be hooked today; encounter start can be hooked via core `'state-changed'` (`explore → combat`) today, without waiting for the combat module; fast travel has no event yet (`ExplorationService.fastTravel()` returns a Promise but `ExplorationEvents` has no `'fast-travel'`), so that one legitimately waits on a §10 core change request. — evidence: `index.ts:144–197` (no subscription to `chapter-changed`/`state-changed`); ARCHITECTURE line 440. — fix: `ctx.events.on('chapter-changed', requestAutosave)`; `ctx.events.on('state-changed', (from,to) => { if (from==='explore' && to==='combat') triggerAutosave(); })` — note this one must fire *in* combat by design (it is the save that carries the `combat` block), so call `triggerAutosave()` directly, not `requestAutosave()`; file a §10 request for an `ExplorationEvents['fast-travel']` event.

4. **Thumbnails will be blank in a real browser.** `renderThumbnail` does `ctx2d.drawImage(gfx.renderer.domElement, …)` from a keydown/timer task (`snapshot.ts:29`), but `Graphics` creates the renderer without `preserveDrawingBuffer` (`graphics.ts:22`), so the WebGL drawing buffer has been cleared after compositing and the capture is black/transparent (JPEG → black). The UI rubric row expects "save/load with thumbnails"; this will surface as a UI defect in wave 2 if not fixed here. — evidence: `snapshot.ts:20–39`, `graphics.ts:22`. — fix: extend `GfxLike` with `render(): void` (Graphics already has it, `graphics.ts:46`) and call `gfx.render()` immediately before `drawImage` in the same task; or request `preserveDrawingBuffer: true` in core (costs performance; the render-then-grab approach is preferred). Also, when the JPEG exceeds 12 KB, retry at quality 0.4/0.3 instead of dropping the thumbnail (`snapshot.ts:33`).

5. **`SaveService.load()` success path is untested.** Tests cover `applyWorldState` directly and the corrupt-save failure path of `load()`, but nothing exercises `load()` succeeding: the `'loading' → 'explore'` state sequence, the `'loaded'` event being emitted after the world is populated, `ui.loading(false)`, or `quest.restore`/`exploration.setDiscovered` being called with the saved data. — evidence: `save.test.ts:178–194` (only the corrupt path); no test registers a fake `quest`/`exploration`/`world` service. — fix: add a test that saves from host A, loads into host B with a stub `quest` (records `restore()` args), stub `exploration` (records `setDiscovered`), stub `world` (records `streamAround` args), and asserts the state events `['loading','explore']`, that a `'loaded'` listener sees `host.world.count() > 0`, and that `loadingCalls` ends with `false`. Add a variant with a stub `combat` whose `restore` resolves and assert `['loading','combat']`.

6. **Active combat with `serialize() === null` silently produces a save without a combat block.** `combatData = combat && combat.isActive() ? (combat.serialize() ?? undefined) : undefined` (`snapshot.ts:52`). Such a save loads into `explore` with units frozen mid-fight. Low today (manual/quick saves are gated to `explore`; combat is a stub) but it becomes live the moment issue 3's encounter-start autosave lands. — fix: `if (combat?.isActive()) { const c = combat.serialize(); if (!c) throw new Error('Cannot save: combat state is not serialisable right now'); combatData = c; }` so the autosave logs a clear error instead of writing a misleading file.

7. **A load that fails before the world is touched still dumps the player to the title screen.** `load()` emits `'loading'` before reading/decoding; a missing slot, a corrupt file or a newer-schema file all throw before `applyWorldState`, yet the catch always requests `'title'` (`index.ts:78`), discarding an intact in-progress game. — fix: decode + migrate first, and only then emit `'loading'` and call `applyWorldState`; in the catch, if the world was not yet reset, request `ctx.state.prev` (the machine exposes `prev`) instead of `'title'`. Keep `'title'` for failures after `resetWorld()`.

8. **Test gaps beyond issue 5.** No test that `encodeSave` throws above `SAVE_MAX_BYTES` (the one line §5.7 explicitly asks to be asserted is only asserted from below); no test for `LocalStorageStore` or `ResilientStore` fallback (a `jsdom`/stub `localStorage` is enough); no IndexedDB test (`fake-indexeddb` is the standard way); no test of the autosave scheduler's gating (construct the `register()` system by hand with a stub scheduler, tick with `state='dialogue'` and assert no save, then `'explore'` and assert one). — fix: add these four tests; the size test can monkey-patch a large `flags` blob rather than 50 000 entities.

9. **`importJson` meta uses the live clock's calendar, and does no structural validation.** `metaFromSave(save, bytes, this.host.clock.calendar().label)` (`index.ts:118`) labels the imported save with the *current* in-game date; the list will show the wrong date. `calendarFromGameTime(save.gameTime).label` exists in `core/clock.ts:53`. Also only `schemaVersion` is checked; `{ "schemaVersion": 1 }` is accepted and produces a row with `undefined` label/location. — fix: use `calendarFromGameTime(save.gameTime).label` in both `save()` and `importJson()`; add a small `assertSaveShape(save)` (checks `world.entities` array, `rngState.world` array, numeric `gameTime`/`seed`) used by `decodeSave`'s caller and by `importJson`, and make `importJson` reject with a clear message on failure.

10. **No in-flight guard between save and load / concurrent saves.** `save()` awaits `existingCreatedAt` (an async decode of the previous file) before `buildSnapshot`; if a `load()` starts during that await, the snapshot is taken from the half-restored world (state `loading`, before `combat.restore`) and written to slot 0. Two autosaves (new-game timer + 10-min bucket) can also interleave on slot 0. Low probability, but cheap to close. — fix: a module-level `busy` promise: `save()`/`load()` chain on it; `buildSnapshot` refuses when `host.state.state === 'loading'`. Also read `createdAt` from the stored `SaveMeta` (add `createdAt` to `SaveMeta` via §10, or keep it in the store row) instead of gunzipping the previous save on every save.

Minor / notable on PASS:
- `ResilientStore` switches to the fallback permanently on the first IndexedDB error, including transient ones (`db.ts:195–199`); the player would then see a different save list. Consider retrying the primary once per operation for `get`/`list`.
- `register()` has no guard against being called twice (Vite HMR re-evaluation) — `defineComponent` in core guards for this, the keydown listener here does not.
- `load()` derives the streaming centre from `exploration.getPlayer()`; `save.playerId` is the authoritative value and does not depend on the exploration module having re-bound its player in a `'loaded'` handler. Prefer `save.playerId` with `getPlayer()` as fallback.
- Cross-cutting (not the save module's fault, for the integrator): `World.clear()` does not fire remove-listeners, and `SaveFile` carries no weather/season. Modules must treat `'state-changed' → 'loading'` as "tear down transient scene objects" and `'loaded'` as "rebuild", or old meshes leak across a load; weather will reset on load until the schema gains a field.
