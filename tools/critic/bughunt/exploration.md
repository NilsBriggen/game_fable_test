# Bug hunt — exploration (src/exploration)

Probes: `tools/critic/probes/exploration/npc-water-spawn.test.ts`, `npc-building-overlap.test.ts` (run: `npx vitest run --config tools/critic/probes/exploration/vitest.config.ts`), both passing (i.e. proving each bug reproduces) against real content (`npc.jost-imhof`/`poi.fluelen`, `poi.luzern`). Cameras 3-4 verified by code reading only (proving *absence* of a check isn't a runtime-probeable fact; no `.test.ts` for those two).

| # | Severity | File:line | Repro | Expected vs actual |
|---|----------|-----------|-------|---------------------|
| 1 | **logic** | `src/exploration/npc.ts:102-121` (`spawnNamed`) | Recruit/encounter any named NPC whose `home` POI sits near a shoreline, e.g. `npc.jost-imhof` (home `poi.fluelen`, a port); probe: `npc-water-spawn.test.ts`. | Expected: no NPC ever spawns standing in water (§5.2's own `walkToward` refuses to *step* into water, and the sibling `spawnGenericFromArchetype` at npc.ts:130-133 explicitly falls back to the POI centre when jittered into water). Actual: `spawnNamed` places the NPC at `home + jitterFor(def.id, 6)` with **no `isWater` check at all** — the fallback that exists for generic crowd NPCs was never added to the named-NPC path, so a named NPC can spawn (and, if its schedule never sends it elsewhere, stay) in the lake. |
| 2 | **logic** | `src/exploration/npc.ts:102-154` (both spawn paths) vs. `settlements.ts:98-116`/`colliders.ts` | Any settlement where a building sits within jitter range of the POI centre, e.g. `poi.luzern`'s chapel/church at `(0,-8)` inside the generic archetype's 14 m jitter radius; probe: `npc-building-overlap.test.ts` (found ≥1 overlap). | Expected: NPCs spawn clear of building footprints the same way the buildings themselves are placed clear of each other (`layout.ts`'s `Builder.add()` calls `overlaps()` against `SPACING`). Actual: neither `spawnNamed` nor `spawnGenericFromArchetype` ever consult the settlement's `Collider[]` (built separately, later, in `rebuildSettlements()`) — NPC placement and building placement are two unrelated coordinate systems, so an NPC can spawn standing inside a house/church mesh. |
| 3 | **logic** | `src/exploration/camera.ts:16-30` (ctor), `:83-101` (`collisionAdjust`) | Stand close against any house/castle wall in follow mode. | Expected: "collision-adjusted" camera per ARCHITECTURE.md §5.2 pulls in from *any* obstruction, matching what the player's own `resolveCollisions` (`player.ts:123`) already collides against. Actual: `CameraRigImpl` is constructed with only `(camera, world, getPlayerPos)` (`index.ts:49`) — it is never given the settlement `Collider[]` the player collides against — and `collisionAdjust` ray-marches only `world.heightAt()` (terrain). The camera can clip straight through a building wall the player is standing next to. |
| 4 | **logic** | `src/exploration/index.ts:105-113` (`rebuildTransientMeshes`) + `src/quest/index.ts:408-415` (`restore`) + `src/save/index.ts:90-98` | Load a save (pause-menu "Load", not a fresh title screen) whose chapter differs from the one already active in the running session — e.g. loading a `ch1-1307` save while currently exploring in `ch2-1314`. | Expected: settlement geometry/colliders and the Gessler-gallows-hat visibility (`showGesslerHat = lastChapter === 'ch1-1307'`) reflect the *loaded* save's chapter. Actual: `restore()` never calls `setChapter`/`populate` or emits `chapter-changed`, so `lastChapter` (only ever written inside `populate()`) is never updated on load; `rebuildTransientMeshes()` only calls `rebuildSettlements()` `if (this.settlementsGroup.children.length === 0)` — true only before the very first populate of the session — so any load after that point silently keeps the *previous* session's collider list and hat visibility. |
| 5 | **perf** | `src/exploration/camera.ts:75-78,84,100,109,123` | Every frame, in `follow` (and `combat`) mode. | Expected: the per-frame camera update does its own math without heap churn, the way `npc.ts`/`poi.ts`/`player.ts` all do (plain-number math, no `Vector3` construction in their `update()` loops). Actual: `orbitPosition()` allocates 3 `new Vector3`s, `collisionAdjust()` allocates 2 more via `.clone()`, plus 1 for `target` — 6 short-lived `Vector3` objects allocated every single frame in the main exploration camera hot loop. |

**Not bugs (checked, clean):** discover-radius firing (`poi.ts:122-132`, thoroughly covered by `poi.test.ts`) — every POI has a positive `discoverRadius`, edge-triggered discovery works at exact radius boundaries. Boat travel never offers an undiscovered port (`interact.ts:83-96` filters `ex.isDiscovered(d)`). Companions left behind after fast travel (`npc.ts:329-336 stepFollow`'s `d > 60` snap fires regardless of frozen state) and across chapter switch (`npc.ts:69-100`, party members survive `clear()`, existing `fixes.test.ts` regression). Interact prompt vs. disabled/sleeping NPCs (`interact.ts:39` filters `!it.enabled`, and `npc.ts:322-323` ties `Interactable.enabled` to the same `asleep` flag that hides the mesh). Rest/trade menus (`interact.ts:59-62`) only reachable via `handleInteractKey`, gated on `state === 'explore'` and `controlEnabled`. No stray `.on()`/`addEventListener` registrations inside per-populate/per-frame code paths (all listener wiring is in `register()`/the service constructor, called once per app boot).
