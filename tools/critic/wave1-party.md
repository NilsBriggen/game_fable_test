## Ranked issues (if FAIL, or notable even on PASS)

1. **XP curve constant is ~60× too high — no skill level-up is reachable in Act 1.** `xpToNext(level) = round(20·(level+1)^1.6)` (`rules.ts:16–17`) gives 927 XP for 10→11 and 31 438 XP for 10→25. With §5.5's per-use values (hit = 5 + tier, kill = 15) a halberdier needs ≈ 4 500 hits ≈ 730 fights for the first perk; Act 1 (~12 fights ≈ 520 XP) does not even reach the first level. The existing test is insensitive to this because it derives its grant from `xpToNext` itself (`party.test.ts:132–134`). — evidence: `node -e` computation above; `rules.ts:17`. — fix: keep the ^1.6 shape and rescale: `xpToNext(level) = Math.max(1, Math.round(5 + 0.3 * Math.pow(level + 1, 1.6)))`. That yields 10→11 = 19 XP (≈ 3 hits — the first "you feel it" moment in fight one), 10→25 = 545 XP (≈ 8–13 fights, 78 hits — first perk two-thirds through Act 1, Skyrim-like), 25→50 = 2 699, 50→75 = 5 838, 75→100 = 9 845, 10→100 = 18 927 per skill. Add a pacing test that pins it: `expect(sum(xpToNext(10..24))).toBeLessThan(700)` and `> 400`, plus `xpToNext(0) >= 1` (a zero cost would loop `applySkillXp` to 100). Also add a `'level-up'`-count test: 12 × `grantSkillXp(id,'halberd',43)` from level 10 must produce ≥ 8 level-ups and ≥ 1 `perk-available`.

2. **Item instance ids collide after load (data corruption).** `instanceSeq` is an in-memory counter starting at 1 (`index.ts:91, 391–393`) and the `'loaded'` handler only invalidates caches (`index.ts:98–100`). After a reload the player's inventory already holds `item-1-1…item-1-5`; the next `addItem` mints `item-1-1` again (probe A: `duplicates ['item-1-1']`). `equip`/`transfer`/`derived` all `find` by `instanceId`, so the wrong sword gets equipped or moved, and `removeItem`'s unequip loop clears the wrong slot. — evidence: probe A; `ecs.ts:203–218` (ids survive load). — fix: in the `'loaded'` handler scan every `Inventory` in `world.query(Inventory)` and set `instanceSeq = max(parsed seq) + 1`; better, drop the owner from the id and generate `item-${++seq}` where `seq` is persisted in `PartyState` (rename to `PartyStateC { formation; nextItemSeq }`) so it survives save/load and never depends on scanning. Add a test: serialize → fresh `PartyServiceImpl` → `world.load` → emit `'loaded'` → `addItem` → assert all `instanceId`s unique.

3. **`derived()` memoisation cannot be invalidated by other modules, and goes stale on direct component edits.** `invalidate` is private (`index.ts:567`); `PartyService` (`services.ts:281–315`) exposes no invalidation method. §5.3 combat will mutate `Character` (fatigue, statuses via `Combatant`), quest effects will edit attributes/inventory, and the exploration/UI builders will edit `Equipment` directly — every such write leaves `derivedCache` stale (probe G: agility 12→20 by direct edit, `defense` stays 11). The `'loaded'` handler also only clears party members' entries, so an enemy's cached stats from before a load survive under a reused `EntityId`. — evidence: probe G; `index.ts:98–100, 567–573`. — fix (pick one): (a) cheapest and safest — drop the cache; `derived()` is ~50 array ops and combat calls it a few dozen times per turn, well inside budget; or (b) keep it but key on a version stamp: `world` already has add/remove listeners — request via §10 a `World.version(id)` bump-on-write, or make `derived()` compare a cheap fingerprint (`JSON.stringify` of attributes+equipment+perk ids+item defIds/qty) before trusting the cache; and (c) in any case clear the *whole* map on `'loaded'` (`derivedCache.clear()`), not just party members. If the cache stays, file a §10 request for `PartyService.invalidate(id)` so combat can call it after status changes.

4. **`removeItem` partially removes when the count is insufficient, and never rolls back.** `removeItem(id,'item.bread',5)` with 3 loaves deletes all 3 and returns `false` (probe B; `index.ts:416–437`). A quest hand-in of "5 bread" that fails still eats the player's food. — fix: `if (this.countItem(id, defId) < qty) return false;` before the loop. Also emit `equipped(id, slot, null)` when the loop unequips a removed instance (`index.ts:426–428`) so the UI hears it.

5. **Equipment slot rules are porous: ammo is not matched to the ranged weapon, a ranged weapon can be in `mainHand` and `ranged` at once.** `slotCompatible('mainHand')` accepts any weapon, including `range`d ones, and `'ammo'` accepts any ammo (`index.ts:350–352`); the same `instanceId` can sit in two slots (probe D: `{ ranged: 'item-1-5', mainHand: 'item-1-5', ammo: bolts-on-a-bow }`). Combat consuming `derived().weapon` and `derived().ranged` will double-count the crossbow, and will draw bolts for a bow. — fix: `mainHand` requires `!def.weapon?.range` unless `'thrown'`; `ammo` requires the equipped `ranged` weapon's `weapon.ammo === def.id` (and unequip ammo when the ranged weapon changes to a different `ammo`); before writing `eq[targetSlot] = instanceId`, remove that instance from any other slot. Also expose the loaded ammo count to combat — `DerivedStats` has no `ammo` field; file a §10 request for `ammo: { defId, instanceId, qty } | null`.

6. **Rest heals nothing for endurance ≤ 9.** `restHeal = hours * (1 + enduranceMod)` (`rules.ts:94–96`) is 0 at endurance 8–9 (probe F). Elder (end 9), child (8), merchant (9), toll-collector (9) never heal, and a player who dumps endurance is stuck at low HP forever. — fix: `hours * Math.max(1, 1 + enduranceMod)` or scale by `hpMax` (`hours * max(1, round(hpMax / 12)) `) — the latter makes an 8-hour rest restore a full bar for everyone, which is what a Skyrim player expects. Also `rest()` does not restore `morale` (§5.3 makes morale the second resource; a night's sleep should reset it to `moraleMax`).

7. **No party-size cap; `addMember` silently builds a 7-member party.** `while (used.has(slot) && slot < 8)` (`index.ts:210`), probe I. §5.5: "Party up to 4 (player + 3)". Exploration/quest builders will trust the service. — fix: `if (this.getParty().length >= 4) { console.warn(...); return; }` (interface returns `void`; prefer a §10 request to return `boolean`). Also refuse an entity without `Character` (later `derived()` throws).

8. **Era gating exists in data but is not enforced anywhere.** `item.langspiess` carries `eraFrom: 'ch2-1314'` (`items.ts:26`), `applyChapter(_chapter)` throws the chapter away (`index.ts:529`), and `equip`/`addItem` never look at `eraFrom` — the 15th-c. pike is equippable in the 1291 prologue (probe K). LORE §7 allows it "only as a Haufen training item at the end of Chapter 2". — fix: store `chapter` on `PartyState` in `applyChapter`, order chapters via a small constant (`['prologue-1291','ch1-1307','ch2-1314']` — align the id strings with the quest builder), and make `equip` return `false` (and `addItem` `console.warn`) when `def.eraFrom` is later than the current chapter. Set `eraFrom: 'ch1-1307'` on `item.langschwert` to match its own note.

9. **Player-facing anachronistic perk names.** `perk.crossbow-100` "Windlass Drill" (`perks.ts:152–156`) puts the banned word in the perk list with the wrong `historical: 'legend'` tag; "Plate Sense" (`perks.ts:226`) and "Push of Pike" (`perks.ts:46`) read as plate harness / pike-era. — fix: rename the capstone to the period-correct spanning method and keep the mechanic — e.g. **"Gürtelhaken-Drill"** ("belt-hook drill": reload as a bonus action), `historical: true`, note on stirrup + belt-hook spanning; then it can be used in Act 1 and the §5.5 example is honoured at a different level. Rename "Plate Sense" → **"Plattenrock"** (the coat-of-plates by its German name) and "Push of Pike" → **"Spiessstoss"**. Optional: "Snapshot" → "Schnellschuss", "Takedown" → "Schwingerwurf". Append one §10 row per renamed/invented perk.

10. **Nothing was registered in LORE §10.** The rubric's pass bar 3 requires every named entity to trace to §1–§7 or §10. Un-traced today: `item.lance`, `item.staff`, `item.leather-cap`, `item.wooden-shoes`/`leather-boots`/`hobnailed-boots`, `item.bandage`/`herbs`/`salve`, and every perk name that is the builder's invention (all of them except Hook / Wall of Iron / Eidgenoss). — fix: append ≈ 6 rows to LORE §10 (one per group is fine: "Habsburg lance", "footwear & leather cap as light protection", "healing consumables per §5.3 Bandage", "walking staff", "perk names (list)", "renamed crossbow capstone"), each with the one-line justification already sitting in the `note` fields.

11. **`addItem` with `qty > 1` on a non-stackable kind creates one instance with `qty 3`.** `STACKABLE_KINDS` excludes weapons/armour/shields, but the non-stackable branch still writes `qty` into a single instance (`index.ts:398–409`, probe C). `condition` is per instance, so three swords must be three instances; `transfer` of a partial qty of such a stack would also split a "unique" item. — fix: in the non-stackable branch loop `qty` times creating separate instances and return the last (or the first); reject `qty <= 0` in both branches. Also `addItem` for an unknown `defId` silently creates a phantom item (`stackable = !def || …`) — throw or `console.warn` and return a `qty 0` instance.

12. **Backgrounds grant kit only, no skill emphasis.** `PlayerCreation.background` is documented as "optional starting skill emphasis" (`services.ts:267`), but `applyStartingKit` touches only items (`index.ts:171–180`). A hunter starts at crossbow 10, a smith at craft 10. — fix: a `BACKGROUND_SKILL_BONUS` table mirroring `ORIGIN_SKILL_BONUS` (+5/+5): hunter crossbow/stealth, smith craft/axe-mace, herder throwing/alpine, fisher athletics/trade, saeumer trade/athletics, novice herbalism/speech; test it like the origin table. With issue 1 fixed, a hunter from Uri starting at crossbow 20 reaches the first crossbow perk in ≈ 4 fights — exactly the "your build matters from fight one" feel.

13. **`transfer` to a dead/unknown entity throws instead of returning `false`.** `this.world.add(to, Inventory, {})` throws `ECS: entity 999 is not alive` (probe E; `index.ts:461`, `ecs.ts:88`). Interface promises `boolean`. — fix: `if (!this.world.has(to, Character) && !this.world.has(to, Inventory)) return false;` (containers will need an Inventory without a Character — check `alive` via a §10 `World.isAlive(id)` or catch the throw).

14. **Events with stale values / missing events.** `level-up` is emitted before `recomputeCharacterLevel` (`index.ts:267` vs `273`), so a listener reading `Character.level` in the handler sees the old character level; equipping a two-hander deletes `offHand` without an `equipped(id,'offHand',null)` event (probe H; `index.ts:374`); `spendAttributePoint` and `recomputeCharacterLevel` change `hpMax` with no `hp-changed`; there is no event at all for a *character* level-up (only per-skill), so the Skyrim "Level Up" toast has nothing to hook. — fix: reorder (recompute first, then emit); emit `equipped(offHand,null)` when clearing; emit `hp-changed` after any `hpMax` change; file a §10 request for `PartyEvents['character-level-up']: [entity, level, attributePointsGained]`.

15. **Test coverage is thin where the bugs are.** 27 tests, none for `removeItem`, `transfer`, `takePerk`/`availablePerks`, `unequip`, ammo matching, `applyChapter`, formation persistence, the `'loaded'` path, or `addMember` limits — i.e. every one of probes A–K was uncovered. — fix: port the probes as tests once fixed (they are 8–10 lines each).
